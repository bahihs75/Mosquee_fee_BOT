# بوت استرجاع مصاريف المهام

هذا مشروع مستقل لبوت تيليغرام خاص يعالج طلبات استرجاع المصاريف التي يدفعها المستخدم الأول خلال مهمة مرتبطة بمسجد أو موقع عمل. يمر الطلب بثلاثة أطراف: المستخدم، مجموعة الإدارة، ثم الصندوق.

## دورة العمل

| المرحلة | المنفذ | النتيجة |
|---|---|---|
| التسجيل | المستخدم | يحفظ البوت الاسم الرسمي مرة واحدة مع معرف تيليغرام ورابط الملف. لا يستطيع المستخدم تغيير الاسم لاحقاً. |
| إنشاء الطلب | المستخدم | يرسل اسم المسجد أو المهمة، الولاية، مدة المهمة، المبلغ، والملاحظات. يمكنه إرفاق صورة أو ملف. |
| مراجعة الإدارة | أي عضو في مجموعة الإدارة | الأعضاء متساوون في الصلاحية. يستطيع العضو اعتماد الطلب، طلب تعديل من المستخدم، تعديل البيانات مباشرة، أو إلغاء الطلب بسبب إلزامي. يسجل البوت اسم ومعرف المنفذ. |
| إعادة التعديل | المستخدم | إذا طلبت الإدارة تعديلاً، يعيد المستخدم إرسال نسخة جديدة؛ تحفظ النسخة القديمة ولا تُمحى. |
| مراجعة الصندوق | المستخدم أو المجموعة المضبوطة كصندوق | لا تظهر أزرار الصندوق إلا للوجهة المضبوطة. يراجع الصندوق الطلب المعتمد، ثم يؤكد الدفع الكامل أو الجزئي إذا فُعّل، أو يرفض/يعلق الدفع بسبب إلزامي. |
| الإغلاق | النظام | عند تأكيد الدفع يُبلّغ المستخدم والإدارة، وتدخل البيانات في Excel. عند رفض الصندوق أو إلغاء الإدارة يُبلّغ المستخدم، وعند إلغاء المستخدم تُبلّغ الإدارة. |

## الصلاحيات

يجب أن يكون البوت موجوداً في مجموعة الإدارة وأن يكون قادراً على قراءة الرسائل ومعالجة الأزرار. لا يعتمد المشروع على قائمة أسماء ثابتة لأعضاء الإدارة؛ بل يتحقق من عضوية منفذ الإجراء في `ADMIN_GROUP_ID`. لذلك يمكن أن تكون المجموعة ذات عضو واحد أو عدة أعضاء، وجميع الأعضاء المقبولين لهم نفس صلاحيات المجال.

المستخدم الأول يستطيع إنشاء طلباته ورؤية سجل طلباته وإلغاء الطلب ضمن الحالات المسموحة. لا يستطيع تغيير اسمه الرسمي. يستطيع أي عضو في مجموعة الإدارة فتح `/users` ورؤية الاسم المسجل ورابط ملف تيليغرام وإجراء تغيير الاسم، ويُسجل التغيير في سجل التدقيق العام.

## التشغيل المحلي

1. أنشئ بوتاً من [BotFather](https://t.me/BotFather)، ثم انسخ `.env.example` إلى `.env` أو صدّر المتغيرات إلى البيئة.
2. أنشئ قاعدة PostgreSQL واضبط `DATABASE_URL`، ثم اضبط `ADMIN_GROUP_ID` إلى معرف المجموعة بصيغة سالبة مثل `-100...`.
3. ثبّت الاعتماديات باستخدام `pip install -r requirements.txt`.
4. شغّل `python app.py` من دون `RENDER_EXTERNAL_URL` لتجربة polling محلياً.
5. أرسل `/start` من حساب المستخدم الأول وأكمل التسجيل.
6. من مجموعة الإدارة استخدم `/help_admin` ثم `/set_cashier user <telegram_id>` أو `/set_cashier group <chat_id>`.

## التشغيل على Render

استخدم `render.yaml` أو أنشئ خدمة Python Web Service. يجب ضبط `RENDER_EXTERNAL_URL` إلى عنوان الخدمة العام، لأن التطبيق يستخدمه لإنشاء webhook على `/telegram/webhook`. يجب ضبط `WEBHOOK_SECRET_TOKEN` ثابتاً وسرياً. يعتمد التطبيق على PostgreSQL للمصدر الدائم، وليس على ملف جلسة تيليغرام.

## أوامر الإدارة

| الأمر | الوظيفة |
|---|---|
| `/users` | عرض المستخدمين المسجلين، الحالة، المعرف، ورابط الملف، مع زر تغيير الاسم. |
| `/export` | إرسال ملف Excel يتضمن الطلبات التي أصبحت `paid_confirmed`. |
| `/set_cashier user <id>` | ضبط مستخدم خاص كوجهة للصندوق. |
| `/set_cashier group <id>` | ضبط مجموعة كوجهة للصندوق. |
| `/help_admin` | عرض تعليمات الإدارة. |

## الحماية من الحالات المتعارضة

يُقفل الطلب داخل معاملة PostgreSQL قبل تغيير الحالة. ولا يسمح التحديث إلا إذا بقيت الحالة والإصدار كما كانا عند بدء العملية. لذلك إذا ضغط عضوان اعتماداً متزامناً، ينجح واحد فقط ويُرفض الآخر برسالة واضحة. كما أن تأكيد الدفع لا ينجح من حالة غير معتمدة أو بعد إغلاق الطلب.

## الإشعارات الفاشلة

كل إشعار يُحفظ في `delivery_messages`. إذا كان المستخدم قد حظر البوت أو كانت مجموعة الصندوق غير متاحة، يبقى الحدث المالي محفوظاً وتُسجّل محاولة الإرسال الفاشلة، ثم تعيد مهمة دورية المحاولة. يمكن للمستخدم مراجعة الحالة من `طلباتي`، ويمكن للإدارة مراجعة سجل الطلب وتصدير المؤكد فقط.

## ملاحظات مالية مقترحة

يُنصح في التشغيل الفعلي بإلزام صورة أو إيصال، وإضافة رقم وصل أو مرجع نقدي، وتحديد سياسة الدفع الجزئي، ومراجعة شهرية لملف Excel مقابل دفتر الصندوق. الإعداد الافتراضي الحالي يمنع الدفع الجزئي ويجعل المرفق اختيارياً إلى أن تقرر الإدارة غير ذلك.
